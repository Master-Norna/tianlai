# Creative Workflow

v0.7 adds an optional, durable governance loop for general-purpose agents working
on a Tianlai authoring project. It lets an agent spend more time reviewing,
rendering, revising, and preserving candidates. It is not a “sounds-good” objective
function, and MCP alone does not make an agent follow it.

## Honest boundary

The workflow separates three kinds of evidence:

| Category | Automatic gate | Meaning |
| --- | --- | --- |
| `hard_failure` | Yes | A trusted engine contract was reproduced. |
| `promise_conflict` | No | The proposal may conflict with the frozen work charter or active clause. |
| `aesthetic_risk` | No | A contextual structural, audible, production, or aesthetic hypothesis. |

Machines can repeatedly eliminate known failures; they cannot thereby prove that
what remains is objectively good. The workflow therefore forbids a single aesthetic
objective and automatic score/audio changes. `accept` means only that the frozen
authority accepted one immutable candidate under this charter, evidence, and stated
perception basis.

Exceptions protect intentional roughness and unknown-but-valuable material. They
must record purpose, scope, higher value, cost, recovery, and evidence. A verified
hard failure can never be excepted. Closing a workflow never deletes an unselected
candidate or an unrevised draft.

## Prerequisites

A workflow is bound to an immutable revision of a persistent authoring project. It
does not replace the score, authoring roster, or render profile, and it never edits
them implicitly.

Start with `creative_workflow_guide`. It returns the modes, boundary, work-charter
template, review phases, evidence contract, decisions, and the identity/hash of the
local official Tianlai Music Constitution v0.2 without injecting the full text.

Fetch only selected official clauses:

```text
get_music_constitution_clauses(
  clause_ids=["C0.04", "C2.1.02", "C4.1.15"],
  language="en"
)
```

At most twelve IDs are accepted. The server verifies the full local document hash
before reading an explicit clause registry; unknown or duplicate IDs fail. Official
activation revalidates document identity, version, language, hash, and every clause
ID. A custom constitution may still be caller-hash-bound, but is identified as
`custom` and cannot impersonate the official document.

A minimal work charter contains:

```json
{
  "title": "work-specific charter",
  "one_sentence_promise": "what this work promises in context",
  "target_listener_and_scene": "listener, scene, medium, monitoring context",
  "primary_sovereignty": ["M"],
  "identity_kernel": {
    "invariants": ["one traceable invariant"],
    "transformable_parts": ["one allowed dimension of change"]
  },
  "ending_contract": "how the ending answers, rewrites, suspends, or refuses the promise"
}
```

The constitution is optional. If used, activate a small work-relevant clause set and
write each clause's role, rationale, and contextual interpretation. Activating
everything turns a review lens into a conservative checklist.

The constitution is not a whole-work prompt injected before generation. Its v0.2
clauses ask questions at positions that change the remaining possibility space;
they do not generate the work's answers. Germinal material and micro-level qiyun
need no item-by-item justification in advance. Once relationships form, major,
salient, or irreversible choices gradually assume consequences proportionate to
their scale. Once the work's own material has settled a question, do not re-argue
the entire piece from constitutional clauses.

At runtime, the wheel reads byte-exact legal-source copies from
`tianlai/_resources/constitutions/` and verifies their fixed full-document hashes.
The Chinese and English originals remain in the music-creation notes, with tests
requiring both locations to stay byte-identical. Clause lookup therefore does not
depend on a source checkout's `docs/` being present in the working directory.

## Xiangyin governance: composition map, mirror, and bounded amendment

Not using MCP provides the baseline for a model's unaided creative ability. When
MCP creates a workflow, this version enables Xiangyin governance by default alongside
the other main workflow capabilities, while retaining an explicit adjustment or
opt-out path. It does not teach imitation through historical works, preference examples,
or winner rationales. Instead it requires the model to explain how **this work**
grows from its own material into a complete sequence:

```text
inspect_workflow_composition for current effective-charter claim IDs
  → draft the composition map
  → inspect_workflow_composition as a read-only whole-work mirror
  → record_workflow_composition_map for this iteration
  → answer every intent / symbolic_structure / orchestration_performance question
      (including a lightweight Chengjing / Qiyun position review inside orchestration)
  → derivation, evidence, rendering, and decision
```

The composition map orders stable nodes and states each node's whole-work function,
charter dependencies, established material, preservation and transformation duties,
role changes, scarce resources, ending response, and open questions. It is not a
fixed-form template, and bar ranges may remain undeclared. Formal candidates are
always complete works; event, bar, and seconds windows are internal locators and
argument scopes, never separately published fragment products.

The mirror reports symbolic facts, map coverage, and question-worthy gaps in the
current score. It neither scores nor edits the work and never claims to have heard
audio. Each governed phase has fixed whole-work questions, with symbolic review also
receiving fact-triggered questions. An answer must cover the exact current set and
cite current claims, nodes, or events relevant to that question. Hinge derivations
also bind the effective charter, map, and already answered questions. The machine
can prove those bindings and coverage, not musical insight or audible quality.

Chengjing / Qiyun is not a new phase. It is a lightweight position review inside
`orchestration_performance`: inspect the complete candidate for places that exist
correctly yet still lack flow, depth, breath, distance, resonance, or peripheral
life. Zero additions must remain a valid outcome; never fill silence with formulaic
ornament merely to complete the pass. Small companion material may be assessed by
deletion, muting, or before/after candidate comparison without inventing a grand
reason or passage-level derivation for every detail. Only an agent that actually
auditioned the complete candidate may record an audition conclusion; otherwise it
records an `aesthetic_risk` or hypothesis awaiting listening. If an edit changes the
identity kernel, primary harmonic causality, section function, climax basis, ending
response, or a charter claim, it has crossed the micro-level boundary and must enter
formal revision. A charter change continues through the existing amendment
preflight; no new phase, ledger, or Schema is introduced. The position scan is
folded into the existing orchestration answer rather than becoming another scored
“Qiyun question.” Software can prove that the prompt was surfaced and references
remain valid, not that the model's creative thought was insightful.

The genesis charter remains immutable. Later changes append to one linear amendment
ledger rather than creating another parent-version tree. A proposed change first
runs `preflight_workflow_charter_amendment`, which exposes affected claims, map
dependencies, derivations, reviews, evidence interpretations, and the minimum
reconstruction scope. Preflight is available while `reviewing`, or after `revise`
while the score is still unchanged. Commit must echo the same preflight hash and
every exact cost field before any replacement score is saved; expanded scope needs
a new preflight. The amendment takes effect next iteration, which must rebuild the
map and repeat whole-work review against the new score and effective charter. A
proposed “revolution” therefore sees and accepts its full cost before it can rewrite
the work and rationalize the result afterward. A non-hard basis must actually reach
an affected claim or collection domain; unrelated feedback cannot authorize an
amendment. The preflight hash includes a minimal resolved-input snapshot, and the
workflow recomputes impact and cost from durable records at commit and on reopen.
Score chronology is proved only by an internal linear save-event chain, not another
parent tree that the creator must manage.

## Modes and state

- `off` records an explicit opt-out and is immediately terminal.
- `audit` reviews a fixed revision or existing candidate and may recommend revision.
- `iterate` renders, reviews, binds explicit new authoring revisions, and selects
  rollback anchors within bounded budgets.

```text
charter_pending
  → activate → map / mirror / question reviews → reviewing
  → request/render → candidate_pending → record → reviewing
  → revise → revision_pending
      → optional amendment preflight/exact cost acknowledgement before score edits
      → bind authoring revision → reviewing → rebuild this iteration's map
  → accept → completed
  → preserve/stop/terminate → stopped
```

Every transition uses `expected_revision`. A complete immutable state revision is
published before the small current pointer advances by compare-and-swap. Normal
`open_creative_workflow` verifies the selected revision only; use the explicit
`verify_creative_workflow_history` audit when the entire parent chain must be proven.

Opening an older revision explicitly sets `historical_read_only=true`. Its
`next_action` only asks the caller to reopen current state without a revision; it
never derives a write recommendation from historical state. Historical revisions
are audit evidence, not CAS write baselines.

`next_action` is procedural navigation, not an aesthetic decision.

Iteration budgets are ceilings, not creative objectives. Accept, preserve, or stop
when the promise has been fulfilled, the identity kernel remains stable through
transformation, and materially distinct alternatives have been closed by explicit
premises. If only surface variants, taste-only differences, or edits unsupported by
new evidence remain, do not iterate merely to perform another iteration.

For direct termination, only `budget_exhausted` has a narrow, reprovable machine
meaning: at least one **positive** frozen budget is at its limit, the current
iteration has reached the fork cap, or workflow history is at its ceiling. A
disabled zero limit is not exhaustion. Other reasons such as
`no_material_improvement` and `external_blocker` remain final-authority
declarations. The state machine checks authority, sequence, and record shape; it
does not present those subjective or external judgements as machine proofs.

## Reviews and evidence

Acceptance requires four current-iteration review phases: `intent`,
`symbolic_structure`, `orchestration_performance`, and `render_report`. The middle
two are render prerequisites under legacy contracts; a governed iteration requires
all first three question-complete phases before rendering. `render_report` is
candidate-bound. Claim
`audio_audition` only after actually hearing the audio.

The stdio MCP boundary has no trusted human identity channel. Generic reviews always
record `reviewer=agent`; no parameter lets a model claim creator, listener, engine,
or validator identity. Generic evidence likewise fixes `reporter=agent` and permits
only `promise_conflict` or `aesthetic_risk`.

Hard failures use `record_verified_workflow_hard_failure(issue_code=...)`. The server
reruns readiness for the iteration's immutable authoring revision and records only
an exact `decision=block` issue reproduced by that trusted boundary.
That record preserves the fact that the failure existed; it is not a permanent
lock. `next_action`, render requests, and acceptance reproduce historical hard
evidence at the trusted readiness boundary. Once the environment recovers,
navigation returns to the normal review/render path without deleting history.

### Claim lifecycle

Reviews, evidence, and exceptions are no longer considered complete merely because
they were appended to a log. Their stable IDs are derived from the complete record
body and are recomputed whenever a revision or history is verified. Rewriting a body
while retaining its old ID fails closed. Evidence-scoped `event_ids` and `part_ids`
are also checked against the immutable authoring score and against each other.
`render_measurement` must bind the current candidate plus one supported report role
(`render_receipt`, `post_render_check`, or `mix_report`) and its hash. Its
`basis.reference` is still a narrative locator; it is not yet presented as a
recomputable JSON-selector/value contract.

Every newly written iteration decision carries two explicit selections:

- `review_ids` freezes the reviews actually adopted by the decision. Acceptance must
  cover all four required phases inside this selected set. An `audio_audition` claim
  also requires a selected audition review by the same decision authority.
- `evidence_dispositions` accounts exactly once for every current non-hard-failure
  evidence record as `resolved`, `accepted_risk`, `excepted`, `deferred`,
  `revision_target`, or `contested`. Resolution and contest require independent
  support rather than self-reference; `contested` cites another evidence claim, and
  `excepted` cites a matching exception that actually references the evidence.

Each disposition's `evidence_id` must also appear in the decision's top-level
`evidence_ids`. Any review, evidence, exception, or derivation ID cited by
`basis_ids` must likewise appear in the corresponding top-level `review_ids`,
`evidence_ids`, `exception_ids`, or `derivation_ids` selection.

Acceptance permits only resolved, consciously accepted, or validly excepted claims;
a promise conflict cannot be demoted to an ordinary accepted risk. Revision and
revision recommendation require at least one `revision_target`; `revise` also requires
`expected_audible_change`. Preserve and stop may honestly retain deferred or contested
claims, which are frozen into terminal `open_evidence_ids`. Direct emergency
termination lists every current non-hard claim as open rather than pretending it was
resolved. Historical decisions and terminations without these additive fields remain
readable and are never backfilled with a false “explicitly empty” interpretation. For
`resolved`, the machine verifies only that basis IDs exist and were selected, rejects
self-reference, and rejects cycles among resolved-evidence dependencies. It does not
prove that the stated resolution is musically or aesthetically sound. This lifecycle
prevents silent omission and body drift; it neither upgrades aesthetic risk into a
hard failure nor decides musical quality for the creator.

A newly written accept also freezes an `acceptance_gate` into the termination. It
rechecks only the hard-failure evidence already recorded in that iteration and binds
the point-in-time authoring revision hash, candidate-manifest SHA-256, those
hard-failure content IDs, and the resulting readiness-result SHA-256 (`null` when
there was no recorded hard failure to check). Acceptance requires none of those
recorded failures to reproduce in that check. This is not current readiness: opening
or verifying history later does not rerun the present machine environment, and the
gate says nothing about new or unrecorded issues. It is also not proof of aesthetic
or musical quality.

Compatibility never backfills old history: legacy, Claim Lifecycle, acceptance-gate,
and settlement shapes keep their original semantics.
`composition_governance_profile=whole-work-derivation-and-bounded-amendment-v1` and
`revision_contract_profile=bounded-change-and-explicit-challenger-settlement-v1`
may exist independently or together. The former governs maps, whole-work questions,
and charter amendment; the latter governs revision scope and challenger closure.
Every new decision explicitly includes `derivation_ids` and
`charter_settlement`; acceptance settles all promises, while preserve/stop may be
partial or empty. Old terminal history
keeps its original semantics and is never backfilled; an old accept without a gate
remains `legacy_unfrozen`. An ordinary older workflow continues to upgrade within
the pre-governance policy and does not acquire a composition-map step merely through
a read or ordinary transition. Governance begins only when a map is explicitly
recorded and cannot downgrade; if the current iteration already has activity,
enforcement begins next iteration. Terminal history remains immutable.
MCP creation enables revision contracts and defaults `composition_governance` to `true`, accepting an explicit
`false` for legacy-flow compatibility. The direct Python API keeps its `false`
default so existing callers do not silently change meaning. Test an unassisted model
baseline without connecting MCP.

## Managed rendering

`render_workflow_candidate` accepts neither paths nor caller-authored authorization.
It performs:

```text
publish sole pending reservation
  → derive exact authorization from that immutable state
  → renderer rechecks that the reservation is current and unconsumed
  → bind the same authorization into receipt and candidate manifest
  → verify project, parent, artifacts, and hashes
  → record the candidate anchor and consume the reservation
```

The binding includes workflow/project identities, reservation revision, iteration,
operation, authoring revision, candidate work/id, and the parent candidate's
work/id/manifest hash. A syntactically valid JSON assertion is not authority.

A disconnected retry reuses and reverifies the same immutable candidate rather than
rendering twice or resetting budget. On failure, the state remains
`candidate_pending`; retry with its current revision or call
`cancel_workflow_render`. A consumed, stopped, superseded, or rolled-back reservation
cannot be replayed.

Candidate inspection reports three separate facts:

- `workflow_authorized`: the exact reservation is in the current immutable history;
- `workflow_recorded`: the current aggregate contains an exact manifest-hash anchor;
- `workflow_accepted`: the terminal accepted selection exactly matches that anchor.

`workflow_managed` is only a compatibility alias for historical authorization.
Atomic authoring renders are false on all three axes. Candidates attached for audit
remain unmanaged and cannot be accepted through that audit workflow.

## Passage-level derivations: why it had to be this way

Evidence records what is wrong; exceptions record why a deviation was
unavoidable. The workflow adds a third record answering why the material on the page
must be there at all:

```text
record_workflow_derivation
```

A derivation is a passage-level affirmative necessity claim. It is not a score
and never blocks anything. It is a scarce argument, not a per-measure quota: record
one only where a choice changes the work's remaining possibility space, such as
identity establishment, a formal turn, climax permission, or the ending. Ordinary
continuation, ornament, and passages with no material alternative need no invented
derivation merely to consume budget.

- **Anchor**: non-empty `event_ids` and/or the complete `start_bar`, `start_beat`,
  `end_bar`, `end_beat` range on the current authoring revision. The score range is
  half-open — `[start_bar:start_beat, end_bar:end_beat)` — so its end is excluded.
  `part_ids` only filter and narrow that scope; they cannot form an anchor alone.
  When combined with `event_ids`, every event must belong to a listed part.
  Candidate-bound `start_seconds` / `end_seconds`, when supplied, are only a
  supplementary rendered-time window and cannot replace an event or bar/beat
  anchor. All referents are verified against the anchored score at record time,
  and the score's canonical hash binds the claim to that exact score revision.
- **Premises**: at least one of four kinds — `declared_promise` (a charter
  field), `active_clause` (an activated clause), `established_material`
  (the work's own prior material, referenced by event_id) and
  `render_measurement` (bound to a candidate artifact hash). Every event in an
  `established_material` premise must start strictly before the target anchor;
  the target itself and future material cannot prove the present choice. The
  strongest form is internal entailment: because the work established something
  earlier, this passage can only follow.
- **Excluded alternatives**: at least one, each with a failure reason and non-empty
  `premise_indexes`. Those indexes are unique, zero-based, and within this
  derivation's `premises`, so every failure explicitly cites its basis. Necessity
  is a claim about alternatives failing; a reason with no alternative or no cited
  premise is only a preference statement.
- **Clauses and sacrifices**: the derivation may list the active clauses it
  invokes and the values it admits sacrificing.

Derivations never block, never trigger an automatic edit and never replace
the ear's final judgement. An accept, revise, recommend, preserve, or stop
decision made through `decide_workflow_iteration` may include `derivation_ids`
so the adopted justifications become part of the decision's durable claim.
The independent emergency termination API does not select a subset, but all
derivations remain in the immutable workflow history and are
covered by `verify_creative_workflow_history`. The budget
`max_derivations_per_iteration` defaults to 8 and may be set to 0 to opt
out entirely. It is an anti-inflation safety ceiling, not a target count.

The audition order is unchanged: listen first, judge, then read the
derivations. They exist to audit whether a judgement holds, not to persuade
the ear before it listens.

The provenance chain is still only half complete. Completion or stopping keeps
derivations in immutable workflow history, and an iteration decision can freeze the
records it adopts through `derivation_ids`. The workflow-managed Candidate v2 and
the separate direct-Score-v2 Candidate v3 are both closed byte sets and neither
embeds that ledger, so a consumer carrying only the candidate cannot inspect it.
A future independent **Candidate Provenance Envelope** / portable bundle should bind
the original candidate manifest hash, terminal workflow revision, and selected
derivations while leaving every candidate byte unchanged. Until that outer contract
exists, never append a sidecar to a candidate directory or render receipt after
acceptance: doing so breaks published closed-set integrity instead of freezing
provenance.

## Charter settlement: the promise ledger

Evidence dispositions settle the problem ledger; charter settlement settles the
promise ledger. The latest policy is marked by
`charter_settlement_profile=affirmative-promise-ledger-v1`, and every new decision
explicitly carries `charter_settlement`, accounting for each affirmative promise of
the frozen charter:

- Targets are enumerated mechanically from the charter: `one_sentence_promise`,
  every `identity_kernel.invariants[i]`, and `ending_contract`.
  `prohibited_shortcuts` are not settlement targets — they are negative
  constraints whose violation still requires a charter-targeted exception.
- Each target is settled at most once, as `kept`, `transformed` or `refused`.
  Constitution v0.2 C6.1.12 permits an ending to complete, rewrite, suspend,
  dissolve, loop, refuse, or stop abruptly. Settlement makes no aesthetic ruling;
  it only requires an honest declaration of how the frozen promise was handled.
- Every settlement item must cite non-empty `basis_ids` among the decision's
  selected reviews, evidence, exceptions or derivations; `transformed`
  requires a derivation basis and `refused` requires an exception or
  derivation basis. Optional `event_ids` are reverified against the anchored
  revision's score both when recorded and on every later history read; resealing
  an edited record cannot preserve a reference to a nonexistent event.
- **Acceptance requires full coverage of every target**; preserve/stop may
  settle partially or not at all, and unsettled promises remain honestly
  unsettled. Historical accepts without the field keep validating under the
  old contract and are never backfilled.

The machine verifies completeness, referential integrity and status legality
only; settlement is an argumentative closure, not an aesthetic proof.

## Fork declarations: whole-work possible worlds

A passage can be written two ways: one stance keeps it restrained, another
lets it soar — and both may stand, like parallel universes, each with its own
necessity. `record_workflow_fork` gives that plurality a container:

- **A branch is always one complete piece, never a replaceable fragment.**
  Each branch references a whole candidate previously recorded in this workflow
  (work_id / candidate_id / manifest hash) plus the stance that world
  embodies and optional current-iteration derivations. The current iteration's
  candidate must be one of the branches. Fragment-level
  substitution is a rendering performance question, not a workflow contract.
- **The anchor** names where the worlds diverge: event_ids and/or an
  end-exclusive bar/beat range on the current authoring revision, with the
  score's canonical hash embedded. part_ids only filter; they never anchor
  alone. When combined, events must belong to the selected parts and lie inside
  the range.
- **`invariant_indexes`** (at least one) point into the charter
  identity_kernel.invariants, claiming which identity invariants hold across
  every branch — the contract basis for "these are still the same piece".
- Forks never block, never rank branches and never replace listening. They realize
  Constitution v0.2 C7.1.02 (a branch must stand as a work) and C7.1.03 (common
  origin does not demand a winner): unchosen worlds are neither deleted nor
  demoted to "failed versions".

At most 8 forks are permitted per iteration. Every read recomputes the ID from
the workflow, iteration, and fork body and reverifies the score's canonical hash,
event/part/range referents, and recorded candidate bindings for all branches.
Reattaching an old ID to an edited body cannot reseal it.

The current fork is a **sparse whole-work alternative declaration**. Record one
only when several complete candidates genuinely need to coexist; it is not a
per-iteration gate and not epoch/LCA lineage. It establishes no branch ancestry,
lowest common ancestor, merge point, or causal evolution—those require a future
independent lineage contract. With no real plurality, decide directly instead of
manufacturing branches to fill a log.

## Decisions, revisions, rollback, and authority

`iterate` supports accept/revise/preserve/stop; `audit` may also recommend revision.
A revision decision must cite evidence. The agent then edits a normal authoring
snapshot, CAS-saves complete documents, and binds that immutable result using
`record_workflow_authoring_revision`. No workflow call secretly creates the edit.

The latest policy also freezes every revise decision into a **revision contract**.
Before editing, `revision_scope` names the documents that may change;
`allowed_document_paths` must use exactly those document keys and may list at most
1024 exact RFC 6901 leaf paths per document. Each path is limited to 1024 characters
and 1024 UTF-8 bytes and grants no prefix or wildcard authority. Score notes never
use array paths: stable `event_ids` and allowed note fields bound them exactly,
bounded revisions cannot reorder them, and each bar range requires `end >= start`.
A scope check covers every persisted save state after the contract causal fence
through the bound target. An intermediate violation is rejected even if the final
documents restore the baseline, so rewrite-then-backfill cannot evade the contract.
A whole-work rewrite must first acknowledge the expanded change surface, downstream
compatibility work, and increased topic-drift risk, with
`allowed_document_paths=null`. `withdrawal_condition` states what evidence would withdraw the
challenger. When the new authoring revision is bound, the machine checks only that
the actual change stayed within this contract. Passing that check never means the
music sounds better.

The next decision closes the prior contract through `prior_revision_assessment`.
Only `promote_challenger` makes the challenger the next editing baseline;
`retain_baseline` and `inconclusive` preserve the frozen complete baseline without
pretending the revision succeeded. A terminating workflow selects that baseline
directly; a continuing workflow rolls back before any further authoring.
The assessment cites selected current-iteration review, evidence, exception, or
derivation records, including at least one current review matching the frozen final
authority and perception basis. `promote_challenger` requires an actual challenger
candidate. If the withdrawal condition is met before rendering, a current
`report_only` review with `candidate_id=null` may support `retain_baseline` or
`inconclusive`; this does not claim that the challenger was heard. Termination preserves the contract baseline, and an unpromoted
challenger cannot replace it merely by being newer.

For a governed workflow, `revision_pending` navigation first separates a score-only
revision from a charter-changing revision. The score-only path proceeds to
`get_authoring_snapshot`. A charter-changing path may read the current score while
weighing the preflight, but it must echo the exact cost and commit the ledger entry
before it may edit or save a replacement score.
The subsequent prerequisites spell out read → evidence- and acknowledged-scope-
bounded complete-document edit → `save_authoring_project` →
`record_workflow_authoring_revision`. `continuation` preserves the workflow ID and
expected workflow revision across the separate authoring CAS save. Legacy contracts
retain the direct score-revision path.

Rollback selects an earlier verified candidate anchor into a new iteration. It does
not move the authoring current pointer, overwrite history, or delete later candidates.
When authoring continues after rollback, content is read from the contract baseline
revision, while the save CAS parent is `authoring_causal_fence.anchor_revision`, the
still-current authoring head. This keeps provenance monotonic without editing from
the withdrawn challenger content.
These guarantees are local to one workflow and one authoring-project chain. A new or
closed workflow and a different project do not inherit the baseline; this version
adds no global singleton, cross-project parent tree, or separate A/B playback system.

Final authority is frozen at workflow creation. Workflows created through stdio MCP
always use `final_authority=agent`; decision, rollback, and stop tools expose no
authority switch. A model call cannot be recorded as creator approval. Human-final
workflows require a trusted host/core API channel, or the MCP workflow should stop
with `human_review_required` and return control.

## Recovery and current maturity

All high-level MCP inputs are path-free: project key, workflow/candidate IDs,
revision hashes, and structured content. Internal candidate paths never cross the
transport boundary. After a CAS conflict or disconnection:

```text
open_creative_workflow
  → read current revision, status, and next_action
  → decide whether the old intent still applies
  → retry, cancel, or stop using the current expected_revision
```

v0.7 established the foundational state, authority, evidence, exception, budget,
immutable-candidate, retry, and audit loop, including a real minimal render through
MCP. `1.0.0` further adds content-ID recomputation, score-referent verification,
explicit per-claim disposition, terminal cross-binding, and current-work composition
maps, question reviews, and bounded amendment. It still cannot replace actual
listening, and it does not use a preference-case library as generation input: that
would invite overfitting, collage, and copying.

- A/B candidates remain a render-kernel and caller-labeling concern; the workflow
  does not duplicate them into a preference-learning system.
- Ensemble concerns enter when actual listening or community feedback produces
  evidence, then trace back to solo, coordination, orchestration, or render causes;
  automation does not pretend to enumerate “correct ensemble” outcomes.
- Further workflow work should strengthen derivation among this work's own material,
  whole-work consistency, and closure rather than feeding prior works into it.
- Preserve complete candidates, first drafts, and material the system does not yet
  understand. Human ears decide comparisons; instruments report only measured facts.
