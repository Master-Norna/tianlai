# 创作工作流

v0.7 增加的是一项可选能力：让通用 Agent 在持久创作工程上多花时间，按证据反复
复核、渲染、修订和保留候选。它不是“好听目标函数”，也不是 MCP 协议本身带来的
保证。生成一段音频和创作一段音乐仍是两回事。

## 诚信边界

工作流把三类判断分开：

| 类别 | 能否自动阻断 | 含义 |
| --- | --- | --- |
| `hard_failure` | 可以 | 可信引擎合同实际复现的失败，如未分配声部、不可渲染输入。 |
| `promise_conflict` | 不可以 | 当前方案可能违背本曲宪章或已激活条款。 |
| `aesthetic_risk` | 不可以 | 结构、听感、制作或审美上的有依据假设。 |

机器可以复利地排除已知失败，却不能据此证明剩余候选“客观好听”。工作流因此明确
禁止单一审美目标、自动改谱和自动改音频。`accept` 只表示：冻结的终审者在这份
work charter、这些证据和声明的感知依据下接受了这个不可变候选。

例外不是检测漏洞。故意粗糙、失真、Lo-fi 底噪、不协和或未被规则理解的材料，可以
用目的、范围、较高价值、代价、恢复方式和证据登记例外。可信 hard failure 永远不能
被例外赦免。未选候选和未修订初稿也不会因 workflow 关闭而被删除。

## 前置条件

工作流依附于一个持久 authoring project 和一个不可变 authoring revision。它不替代
score、authoring roster 或 render profile，也不替 Agent 暗中修改它们。

Agent 应先调用：

```text
creative_workflow_guide
```

该工具返回模式、边界、work charter 模板、复核阶段、证据合同、允许决策，以及本地
官方《天籁音乐宪法 v0.1》的身份和 Hash。它不会把 901 行全文塞入每轮上下文。

如需官方条文，按明确 ID 有界读取：

```text
get_music_constitution_clauses(
  clause_ids=["C0.02", "C0.03", "C0.25"],
  language="zh-CN"
)
```

一次至多 12 条。服务先核对完整文档 SHA-256，再从明确注册表返回条文；未知 ID、
重复 ID、文档缺失或完整性不符都会拒绝。官方 activation 还会再次核对
`document_id`、`version`、`language`、`content_sha256` 和全部激活 ID。自定义宪法仍可
只按 caller 提供的 Hash 与解释绑定，但结果明确标为 `custom`，不能冒充官方文档。

## Work charter

最低可用宪章如下：

```json
{
  "title": "本曲宪章标题",
  "one_sentence_promise": "这首作品在此语境中承诺什么",
  "target_listener_and_scene": "听众、场景、媒介与监听条件",
  "primary_sovereignty": ["M"],
  "identity_kernel": {
    "invariants": ["必须可追踪的不变量"],
    "transformable_parts": ["允许改变的部分"]
  },
  "ending_contract": "结尾如何回答、改写、悬置或拒绝开头承诺"
}
```

还可声明情绪与运动向量、能量/张力曲线、记忆地标、稀缺资源、高潮特权、禁止捷径、
不确定性和终审维度。`primary_sovereignty` 使用 `M/G/H/P/T/O/N/L/R/C/X/I` 等法域
代码；它不是风格分数。

宪法是可选的。采用时只激活少量、与本曲直接相关的条款，并为每条写明
`role`、`rationale` 和本曲语境下的 `interpretation`。全开条款会让规则互相稀释，
也会把工作流退化成保守清单。

运行时从 wheel 内 `tianlai/_resources/constitutions/` 读取经固定完整 Hash 校验的
byte-for-byte 法源副本；音乐创作参考笔记中的中英文原文继续保留，并由测试强制两处
字节同步。因此条文查询不依赖当前目录恰好存在源码仓库的 `docs/`。

## 模式与状态

| 模式 | 用途 |
| --- | --- |
| `off` | 留下明确 opt-out；创建后即为 `disabled`。 |
| `audit` | 审查固定修订或既有候选，可建议修订，但不进入自动迭代链。 |
| `iterate` | 在预算内渲染、复核、绑定显式新修订和回滚选择。 |

主要状态迁移为：

```text
charter_pending
  → activate → reviewing
  → request/render → candidate_pending → record → reviewing
  → revise → revision_pending → bind authoring revision → reviewing
  → accept → completed
  → preserve/stop/terminate → stopped
```

每一步都要求 `expected_revision`。状态以完整不可变修订发布，再用小型 current pointer
做 CAS；旧修订和父链保留。普通 `open_creative_workflow` 只验证所选修订，避免每步
产生 O(n²) 历史遍历；需要审计时显式调用 `verify_creative_workflow_history`。

显式打开旧修订时，结果标记 `historical_read_only=true`；其 `next_action` 只会要求
不带 revision 重新打开 current，不会根据历史状态建议任何写操作。历史修订用于审计，
不能作为新的 CAS 写入基线。

`next_action` 根据当前已验证状态给出程序导航和建议参数，但不替终审者选择作品。

## 复核与证据

接受候选前，本轮必须记录四相复核：

1. `intent`
2. `symbolic_structure`
3. `orchestration_performance`
4. `render_report`

其中结构和配器复核是渲染前置；`render_report` 必须绑定当前候选。只有实际听过音频的
主体才可声明 `audio_audition`。stdio MCP 没有可信人类身份通道，所以 generic review
始终记录 `reviewer=agent`；它没有让模型自称 creator、listener、engine 或 validator
的参数。

普通 `record_workflow_evidence` 也固定 `reporter=agent`，schema 只允许
`promise_conflict` 和 `aesthetic_risk`。`render_measurement` 必须把 artifact Hash 与
`render_receipt`、`post_render_check` 或 `mix_report` 的明确角色绑定，不能拿任意 Hash
冒充测量证据。

hard failure 走独立可信入口：

```text
record_verified_workflow_hard_failure(issue_code=...)
```

服务端会针对本轮固定 authoring revision 重新运行 readiness，只接受其中
`decision=block` 且代码精确相等的 issue，并持久化为 validator/engine-contract 证据。
这份记录保留“当时确实失败”的历史事实，但不是永久封锁：`next_action`、渲染请求和
accept 都会在可信 readiness 边界重新复现；环境恢复后，导航会回到正常复核/渲染路径，
而不会因为旧证据仍在历史中就强迫无意义修订。

## 受管渲染授权链

高层 `render_workflow_candidate` 不接受路径，也不接受 caller 构造的 authorization。
内部闭环为：

```text
当前 reviewing 修订
  → 发布唯一 candidate_pending 预留
  → 从预留生成精确 authorization
  → 渲染器再次确认预留仍为 current 且未消费
  → 同一 authorization 写入 render receipt 与 candidate manifest
  → 候选完整性、工程修订、父候选和工件 Hash 复验
  → workflow 记录候选锚点并消费预留
```

authorization 同时绑定 workflow、工程、预留修订、迭代、操作、authoring revision、
候选 work/id，以及父候选 work/id/manifest Hash。复制一份 shape 正确的 JSON 不是权限。

相同操作在断线后重试会复用并复验同一候选，不重复渲染或重置预算。若渲染失败，
状态保留在 `candidate_pending`，失败结果带当前快照；调用者可按新修订重试，或调用
`cancel_workflow_render`。旧预留在消费、停止、回滚或 current pointer 前进后不能重放。

## 候选的三个事实

`inspect_authoring_candidate` 分开报告：

- `workflow_authorized`：该 authorization 确实来自当前完整历史中的不可变预留；
- `workflow_recorded`：当前 workflow aggregate 中存在与 manifest Hash 完全一致的候选锚点；
- `workflow_accepted`：终止记录以四相复核后的 accept 精确选择了这个候选。

`workflow_managed` 只是兼容字段，仅在 `workflow_authorized=true` 时为真。一个候选可以
已授权但尚未记录，也可以已记录但尚未接受；三者不能互相冒充。普通原子 authoring
渲染三项都为假。audit 接入的既有候选保持 unmanaged，不能通过该 workflow accept。

## 决策、修订与回滚

`iterate` 允许 `accept`、`revise`、`preserve`、`stop`；`audit` 还可
`recommend_revision`。`revise` 必须引用本轮证据，并进入 `revision_pending`。Agent 随后
通过正常 authoring 工具读取、编辑并 CAS 保存完整 documents，再用
`record_workflow_authoring_revision` 绑定新修订。没有任何 workflow 调用会偷偷产生这份
修改。

此时 `next_action.operation` 会指向可直接调用的 `get_authoring_snapshot`，并带上
`project_key` 和本轮锚定修订。`prerequisites` 明列“读取 → 只做有证据的完整文档编辑 →
`save_authoring_project` → `record_workflow_authoring_revision`”四步；`continuation` 保留
workflow ID 与预期 workflow 修订，因此 authoring CAS 保存不会丢失返回工作流的位置。

`rollback_creative_workflow` 选择较早迭代的已验证候选锚点，生成新迭代；它不移动
authoring current pointer、不覆盖旧修订，也不删除失败或未理解的候选。

## 权限

终审身份在创建时冻结。由 stdio MCP 创建的 workflow 永远使用
`final_authority=agent`；decision、rollback 和 stop 工具没有 authority 参数，而是核对
冻结值。MCP 不能把一次模型调用写成“创作者已批准”。

需要人类终审时，应由可信宿主入口创建 `final_authority=creator` 的核心 workflow，
或让 MCP workflow 以 `human_review_required` 停止。Agent 可以提供证据和候选，但身份
不能靠 caller 自述升级。

## 路径与恢复

所有高层 MCP 工具只接收 `project_key`、workflow ID、修订 Hash、候选 ID 和结构化
内容。服务端把工程映射到固定 authoring namespace，输出不含本机路径。受管 render
与 record 之间需要的候选绝对路径只在服务内部短暂使用。

语义错误返回稳定、无路径的 `error.code`。CAS 冲突或断线后的正确恢复顺序是：

```text
open_creative_workflow
  → 读取当前 workflow.revision、status 与 next_action
  → 重新判断原操作是否仍适用
  → 用当前 expected_revision 重试、取消或停止
```

不要盲重放旧 revision。需要证明完整父链时，显式调用历史验证工具；这是一项审计，
不是每次状态读取的隐性成本。

## 实际曲目验证前的边界

v0.7 已把状态、权限、证据、例外、预算、不可变候选、重试和审计链闭合，并用真实最小
渲染验证 transport 与工件绑定。它尚不能替代实际曲目的听测判例。后续成熟度来自：

- 对真实作品填充 C8.2 A/B 听测和判例，而不是训练单一“好听分数”；
- 观察哪些失败模式跨作品重复成立，再谨慎扩充负知识；
- 保留帕累托候选、未修订初稿与暂时无法解释的材料；
- 让人耳决定比较关系，让仪表只陈述它真正测到的事实。
