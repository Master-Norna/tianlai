# 从乐谱到第二次渲染

这一页是推荐主流程。目标不是只得到一个 WAV，而是完成一次可以继续修改、
可以比较前后版本的创作闭环：

```text
安装 → 导入 → 明确配器 → 候选 1 → 定位问题 → 修改 score → 候选 2 → A/B
```

以下命令都在源码发布包根目录的“命令提示符（cmd.exe）”执行，多行续写符为
`^`。Windows 用户可以直接使用 `天籁.cmd`；它固定调用项目自己的 `.venv`，
不会污染系统 Python。

## 1. 安装并检查

```cmd
安装运行环境.cmd
检查运行环境.cmd
```

第一次命令会创建 `.venv`、安装核心与 MCP、执行环境诊断，并用不依赖外部采样的
参考振荡器生成首次出声 WAV。它不会下载数 GB 音源。

环境诊断会分别报告：

- 代码和目录是否可运行；
- 103 件正式声音入口中有多少资源 `ready`、`missing` 或 `invalid`；
- 可信调色板是否可用；
- 缺失资源是否已有恢复安装器。

缺少某件采样资源时，渲染会明确失败，不会静默换成通用 GM 音色。当前有 29 件
项目自研 DSP 入口无需外部采样；其余 74 件外部资源均有根级恢复路径。先查看
许可、体积和本机状态：

```cmd
安装可恢复音源.cmd -PlanOnly
```

确认后再运行 `安装可恢复音源.cmd`。无参数模式处理全部 74 件外部资源，也可按
资源族或组只安装需要的子集。脚本完成表示所选资源通过固定归档/完整树证据，不
代表取得第三方采样的再分发权；实际就绪数仍以 `检查运行环境.cmd` 为准。

### 先跑仓库自带闭环

如果暂时没有自己的 MIDI/MusicXML，可用 `examples/最小闭环.musicxml` 熟悉
流程。它只有一个 `P1` 声部，配套文件包括：

- `最小闭环.render-profile.json`：轻量、确定性的候选配置；
- `最小闭环.slice-query.json`：读取 `P1` 的有界片段；
- `最小闭环.patch.json`：把最后一个 G4 修改为更重的 F4；
- `乐器/测试工具/参考振荡器`：无需下载采样。

下面各节把“某曲”替换成“最小闭环”，导入命令使用：

```cmd
天籁.cmd project-import ^
  --input "examples\最小闭环.musicxml" ^
  --output "output\入门闭环\导入-01"
```

接着可以直接复制下面两条命令完成配器确认与第一次出声：

```cmd
天籁.cmd roster-promote ^
  --score "output\入门闭环\导入-01\最小闭环.score.json" ^
  --draft "output\入门闭环\导入-01\最小闭环.roster-draft.json" ^
  --assign "P1=测试工具/参考振荡器" ^
  --open-palette ^
  --output "output\入门闭环\最小闭环.roster.json"
```

```cmd
天籁.cmd project-render ^
  --score "output\入门闭环\导入-01\最小闭环.score.json" ^
  --roster "output\入门闭环\最小闭环.roster.json" ^
  --render-profile "examples\最小闭环.render-profile.json" ^
  --title "最小闭环"
```

成功后，终端返回的 `mix_wav` 就是第一次出声的绝对路径。后续切片可以直接使用
配套 query，补丁可以直接使用配套 patch；第二次 `project-render` 仍需增加同一
份 `--render-profile`。该固定补丁只绑定这份示例导入得到的原始 score，不要把它
用于自己的谱。下面第 2 节起使用的是自有曲目的通用路径模板，不要把其中
`乐谱\曲目\某曲` 的路径机械套到这个 `output\入门闭环` 示例上。

## 2. 把谱面导入一个新工程

MuseScore 等制谱软件通常可以导出 MusicXML；DAW 和制谱软件通常也可以导出
标准 MIDI。MusicXML 更适合保存谱面结构，MIDI 更适合保存实际演奏时序和逐音
力度，但两者都可能包含天籁当前无法无损表达的语义。

```cmd
天籁.cmd project-import ^
  --input "乐谱\曲目\某曲\MusicXML\某曲.mxl" ^
  --output "乐谱\曲目\某曲\导入-01"
```

MIDI 只需把 `--input` 换成 `.mid` 或 `.midi`。命令默认：

- 生成 `某曲.score.json`、`某曲.import-report.json` 和
  `某曲.roster-draft.json`；
- import report 与 roster draft 同时记录源文件字节 Hash 和规范化 score Hash；
- 拒绝覆盖现有导入目录；
- 对无法保留的演奏语义执行 `--loss-policy reject`；
- 只给出有界的候选乐器提示，不自动取得配器权限。

默认 `reject` 命中未支持语义时会原子失败，不发布 score、report 或 draft 的
半套文件。若错误指出的降级经过人工确认可以接受，再显式重跑到一个新目录：

```cmd
天籁.cmd project-import ^
  --input "乐谱\曲目\某曲\MusicXML\某曲.mxl" ^
  --output "乐谱\曲目\某曲\导入-02" ^
  --loss-policy warn
```

`warn` 成功后不要只看终端一句成功信息；保存并阅读完整的
`import-report.json`。重复、倚音、踏板、
弯音、厂商控制器等未进入 score 的信息无法靠后续渲染自动恢复。

## 3. 显式确认每个声部的乐器

打开 `roster-draft.json`，查看每个声部的 ID、音域、打击乐标记和
`routing_hints`。候选只帮助缩小范围；最终路由由创作者确认。

普通旋律声部可以直接在命令行逐项指定：

```cmd
天籁.cmd roster-promote ^
  --score "乐谱\曲目\某曲\导入-01\某曲.score.json" ^
  --draft "乐谱\曲目\某曲\导入-01\某曲.roster-draft.json" ^
  --assign "Piano=键盘乐器/钢琴" ^
  --assign "Violin=管弦乐/弦乐组/小提琴" ^
  --output "乐谱\曲目\某曲\某曲.roster.json"
```

`--assign` 左侧必须精确等于 `score.parts[].id`，也就是 draft 中对应的
`assignment.part`；不要使用只供显示的 `parts[].name`。鼓组或需要角色、增益、
座位、声部组和协奏关系的工程，使用一个 `assignments.json`：

```json
[
  {
    "part": "Melody",
    "instrument": "管弦乐/弦乐组/小提琴",
    "gain_db": -3,
    "role": {
      "function": "lead",
      "prominence": "foreground"
    }
  },
  {
    "part": "Drums",
    "kit": {
      "C2": "现代鼓组/底鼓",
      "D2": "现代鼓组/小军鼓"
    }
  }
]
```

```cmd
天籁.cmd roster-promote ^
  --score "...\某曲.score.json" ^
  --draft "...\某曲.roster-draft.json" ^
  --assignments "assignments.json" ^
  --output "乐谱\曲目\某曲\某曲.roster.json"
```

默认只允许当前可信调色板。需要使用其他未隔离正式入口时，配器确认阶段显式加入
`--open-palette`。许可证据隔离和本机 SoundFont 兼容入口不会因此被放开。

## 4. 生成第一个不可变候选

```cmd
天籁.cmd project-render ^
  --score "乐谱\曲目\某曲\导入-01\某曲.score.json" ^
  --roster "乐谱\曲目\某曲\某曲.roster.json" ^
  --title "某曲"
```

默认使用版本化的 `preview-v1` 配置：确定性 seed、共享厅堂、峰值归一到
`-1 dBFS`、保存分轨并启用原始分轨缓存。输出位于：

```text
output/候选/<安全化作品名>/<唯一候选 ID>/
```

候选目录包含：

- `合奏.wav` 和可选 `分轨/`；
- `score.json`、`roster.json`、`render-profile.json`；
- `演奏计划.json`、`渲染回执.json`；
- `渲染后自检.json`（绑定最终 PCM、标准响度/True Peak 测量与分级风险）；
- `许可与署名.json/.txt`；
- 最后写入的 `候选.json`。

`候选.json` 将这些文件和实际演奏计划绑定。默认不会用同名标题覆盖旧成品；标题
也不会再造成 MCP 输出碰撞。

候选先在同一父目录的私有 staging 中完整渲染。引擎重新流式读取最终 PCM，递归
校验回执绑定的演奏计划、自检、合奏、分轨、许可旁车、署名与诊断，再原子发布到
最终目录，并在最终路径二次
复验。受控覆盖同时绑定旧回执和准备时看到的旧候选清单，可拒绝并发写者的过期
授权；普通异常会保留或恢复上一份完整候选。

自检中的 `error` 只表示可证明的合同失败；True Peak 余量、响度、DC、相位、
声道和尾音候选属于非阻断复核项。完整边界见
[渲染后自检](渲染后自检.md)。

## 5. 从听到的秒数回到音符

假设在 `34.2` 秒听到异响：

```cmd
天籁.cmd candidate-locate ^
  --candidate "output\候选\...\candidate-..." ^
  --at 34.2 ^
  --output "output\诊断\34.2秒.json"
```

这个命令读取已保存候选的回执和演奏计划，不会重新编译已经修改过的当前工程。
它会返回：

- 该秒正在门控发声的事件；
- 最近结束、可能仍有采样释音或厅堂贡献的事件；
- 紧接着将发声的事件；
- `event_id`、声部、乐器、音高、小节、拍位和所有绑定 Hash。

尾音列表是候选来源，不是假装完成逐样本因果分析；最终仍需结合分轨和人耳判断。

## 6. 有冲突保护地修改 score

先读取一个有界片段。保存下列查询为 `slice-query.json`：

```json
{
  "kind": "tianlai.score_slice_query",
  "schema_version": 1,
  "part_ids": ["Violin"],
  "bar_range": {"start": 12, "end": 14},
  "max_notes": 128
}
```

```cmd
天籁.cmd score-slice ^
  --score "乐谱\曲目\某曲\导入-01\某曲.score.json" ^
  --query "slice-query.json" ^
  --output "slice-result.json"
```

结果中的 `score_sha256` 是修改基线。保存补丁为 `patch-01.json`：

```json
{
  "kind": "tianlai.score_patch",
  "schema_version": 1,
  "base_score_sha256": "从 slice-result.json 复制的 64 位 Hash",
  "operations": [
    {
      "op": "update_note",
      "event_id": "violin-0042",
      "expect": {"pitch": "B5", "dynamic": "f"},
      "changes": {"pitch": "A5", "dynamic": "mf"}
    }
  ]
}
```

```cmd
天籁.cmd score-patch ^
  --score "乐谱\曲目\某曲\导入-01\某曲.score.json" ^
  --patch "patch-01.json" ^
  --output "乐谱\曲目\某曲\某曲.rev02.score.json" ^
  --result-output "乐谱\曲目\某曲\某曲.rev02.patch-result.json"
```

Hash 或 `expect` 旧值不一致时，整批补丁都会拒绝，不会只改一半。移动、改音高、
力度或时值时保留原 `event_id`；新增音符的 ID 由引擎确定性分配。熟悉 JSON 的
创作者也可以直接编辑副本，但要保留 ID，并避免再次运行会覆盖该文件的旧生成器。

## 7. 生成第二个候选并比较

使用新 score 再渲染，并把第一个候选 ID 记为父版本：

```cmd
天籁.cmd project-render ^
  --score "乐谱\曲目\某曲\某曲.rev02.score.json" ^
  --roster "乐谱\曲目\某曲\某曲.roster.json" ^
  --title "某曲" ^
  --parent-candidate "candidate-第一个候选ID"
```

只改 gain、pan、座位、厅堂、master 或归一设置时，经过完整身份校验的原始分轨
缓存可以直接重混；改动某声部音符、奏法、音源、乐器参数或 DSP 后，只让相关
缓存失效。

```cmd
天籁.cmd candidate-compare ^
  --before "output\候选\...\candidate-第一个" ^
  --after "output\候选\...\candidate-第二个" ^
  --output "output\诊断\候选1-候选2.json"
```

比较结果会区分 score、roster、render profile、演奏计划和最终 mix 身份变化。
然后直接 A/B 两个目录中的 `合奏.wav`；机器差异只帮助确认“改了什么”，不判断
哪一版更好听。

## 8. 需要回到制谱软件时

score 是天籁的权威可编辑中间态。若要在 MuseScore 或 DAW 里继续编辑，可以导出
一个明确标注损失的 MIDI 副本：

```cmd
天籁.cmd export-midi ^
  --score "乐谱\曲目\某曲\某曲.rev02.score.json" ^
  --roster "乐谱\曲目\某曲\某曲.roster.json" ^
  --output "乐谱\曲目\某曲\MIDI\某曲.rev02.mid"
```

默认遇到阻断性语义损失时只写 loss report，不写 MIDI。确认报告后才传
`--allow-lossy`。MIDI 不保留天籁的稳定事件身份、全部奏法、微分音、乐句和专用
乐器语义，因此它是交换/编辑副本，不是 score 的无损逆变换。

## 失败时先看什么

1. `检查运行环境.cmd`：区分代码、可信清单和实际音源缺失；
2. `import-report.json`：确认导入语义损失；
3. `roster-promote` 错误：确认每个声部都有且只有一个明确路由；
4. `candidate-locate`：按实际听到的候选定位，不用修改后的工程猜；
5. `许可与署名.json`：发布输出前核对本次实际资源；
6. `docs/当前状态.md`：确认未验收范围和已知性能限制。
