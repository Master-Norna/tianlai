# 当前能力与限制

> 版本：`1.1.0`
>
> 更新日期：2026-08-25

本页说明使用者能够依赖的功能与已知边界；本机乐器和音源是否可用，以
环境诊断命令 `tianlai-doctor` 的当次结果为准。

## 产品定位

天籁是一套本地运行、可编辑、可复算的音乐执行与迭代工作台：

```text
导入谱面 → 明确配器 → 渲染不可变候选
    → 从听到的秒数定位事件 → 局部修改 score
    → 渲染第二个候选 → 机器比较 + 人耳 A/B
```

CLI 与 MCP 使用同一套乐谱、配器、渲染和候选合同，但文件权限与默认输出位置
不同。完整教程见 [从乐谱到第二次渲染](从乐谱到第二次渲染.md)。

## 平台支持

| 环境 | 支持范围 |
| --- | --- |
| Windows 10/11 x64 | 完整参考平台；支持最小安装、全部资源恢复入口、CLI、MCP 与首次出声 |
| Linux / WSL x86_64 | 支持独立环境、环境诊断、程序音色、CLI、MCP、portable 自检，以及全部 74 件外部资源的跨平台恢复入口 |
| macOS 15 / 26 `arm64` / `x86_64` | 支持独立原生环境、环境诊断、程序音色、CLI、MCP、portable 自检，以及全部 74 件外部资源的跨平台恢复入口；macOS 15 的两种架构均配置 CPython 3.11–3.14 完整矩阵，macOS 26 的两种架构复验 3.14；以合入后的实际 CI 结果为准 |
| CPython | 支持 64 位 CPython 3.11–3.14 |

macOS 合同只接受原生进程；启动入口和 doctor 会识别并拒绝 Rosetta 翻译态。

`1.0.0` 在既有 Windows 8.3 与 macOS 路径别名安全边界上，继续使用自动受管
worker、长轨分块流式渲染和本机自适应调度；这些优化不新增 `render profile`
参数，必需的身份、资源或预检预算证据不足都会回退到原有串行路径。发布构建器仍会在解析路径身份前拒绝
符号链接和重解析点，Python 源码仍固定以 LF 检出。

15 个资源族的跨平台恢复器覆盖全部 74 件外部资源。大型第三方归档仍由使用者
按各自上游许可在本机下载，普通 CI 不下载这些资源；缺失或不匹配时不会静默替换
音色。详情见 [Linux / WSL 快速开始](Linux快速开始.md)与
[macOS 快速开始](macOS快速开始.md)。

## 声音入口与资源

项目登记 103 个正式声音入口，另有一个只用于自检的参考振荡器：

- 29 件采用项目自研 DSP、合成或程序拟音，不需要第三方音频资产；
- 74 件依赖外部公开资源，源码包不携带这些大型采样；
- Windows、Linux 与 macOS 均为全部 74 件提供统一的根级 Python 恢复入口；
- 清单冻结 15 个资源族的公开上游、许可、归档或提交身份、安装树摘要和证据文件；
- 平台入口可用不等于大型资源已经下载，也不等于完成了所有真实采样试听。

资源缺失时渲染会明确失败，不会自动换成通用 GM SoundFont。先用环境诊断查看
状态，再按平台文档读取计划和安装所需资源。

## 质量状态

103 个声音入口的当前绑定版本均完成了单乐器、单音色独立试听，因此标记为
`quality_tier=formal`。这个术语只描述当前绑定音色，不表示以下事项已经全部
完成：

- 所有音高、力度、奏法与 Round Robin 组合；
- 所有多乐器编配、混音与厅堂组合；
- 专家对每种真实乐器细节的评价；
- 第三方资源的再分发授权；
- 任意作品都能自动获得理想听感。

`collaboration_review_status=untested` 表示合奏语境仍需按作品实际试听。
`strict_hq` 是缺少精确证据时拒绝执行的门禁，不是自动增强音质的开关。

## 已实现能力

### 导入与可编辑乐谱

- `project-import` 统一处理 MIDI、MusicXML/XML 与 MXL；
- 成功导入生成 score v1、导入报告和不可执行的 roster 草稿；
- 无法无损表达的源语义会按明确的 loss policy 报告或拒绝；
- score v1 使用稳定 `event_id`，并可保留 MusicXML 的 `staff` 与 `voice`；
- `score-slice`、`score-patch` 和 `score-compare` 支持有界读取、原子修改和
  版本比较。

MIDI 与 MusicXML 都不是无损万能入口。踏板、弯音、歌词、排版和厂商控制信息等
超出当前模型的内容，以导入报告为准。

### Score v2 与受限正式渲染

- Score v2 使用有理数时间、稳定事件身份、书写/实音音高和显式 tie/phrase 关系；
- `migrate-score-v2` 可以把可精确表达的 score v1 迁移为带回执的 v2 bundle，但迁移本身不渲染；
- `project-render-v2` 直接消费 score v2，使用精确采样时间、execution profile、能力证据和
  活跃 runtime authority lease 生成 PCM24、渲染后自检、正式回执与 Candidate v3；
- Candidate v3 封闭绑定 score、roster、execution profile、中间计划、运行时证据与最终 WAV，
  旧 Candidate v1/v2 仍按原合同验证。

首版 direct-v2 正式链只接受单 executor、内置 oscillator、零外部资产、
`tail=0` 和源码工作区。采样、自定义、懒加载资产与多 executor 路径会明确拒绝，
不会降级到旧 conductor 或通用音色冒充成功。

### 配器、渲染与候选

- 每个普通声部必须显式选择乐器，打击声部必须显式选择 kit；
- `project-render` 默认创建新的唯一候选，不覆盖旧结果；
- 候选绑定 score、roster、render profile、演奏计划、音频、回执与许可旁车；
- 单乐器与合奏从写盘后的最终 PCM 生成 `渲染后自检.json`；新 v3 回执绑定报告，
  旧 v2 回执保持可验；
- 自检按 BS.1770 / EBU Mode 测量 True Peak、LUFS 与 LRA，并记录结构、DC、
  立体声、数字零、满幅和首尾证据；只有可证明的损坏与合同矛盾阻断，创作风险
  保持非阻断；
- `candidate-verify` 对候选执行描述符绑定的封闭代际核验，拒绝额外工件、链接、硬链接和
  检测到的身份或内容漂移；完整性成功不等于作者或来源认证，也不冻结命令
  返回后的现场目录；
- `candidate-locate` 从实际候选秒数定位事件；
- `candidate-compare` 区分乐谱、配器、配置、计划和混音变化；
- 分轨缓存可加速只改变 gain、pan、座位、厅堂、master 或归一化后的重混；
- 对满足信任、资源和工作量边界的分轨，引擎可自动使用最多四个受管 worker，并
  以分块流式方式写入缓存和混音；并行与串行产物保持同一正式字节合同；
- 本机调度只学习已经完整验证并提交的成功任务；学习状态损坏、证据不足或收益不
  明确时保持静态策略或串行执行，不影响渲染正确性。

候选用于试听、定位或比较后，应视为不可变快照。修改应回到 score、roster 或
render profile，再产生下一代候选。

### AI 与 MCP

MCP 提供合同读取、乐器发现、导入、显式配器、预检、渲染、定位、局部修改、
候选比较，以及 v0.7 的 path-free 作者工程与可选创作工作流。工作流可冻结单曲
宪章；立宪后若需另一个思想角度，可另外无状态查询少量外部宪法条文。工作流记录分层复查与证据，以 CAS
预留并认领受管候选，再进行有界
修订、回退或停止。`1.0.0` 新增 Claim Lifecycle v1：重算主张内容 ID、复验
谱面指涉、要求决策逐条处置本轮主张，并在终局冻结开放项；它还可记录段落级必然性
推导（为何不得不如此），锚点指涉按当前修订谱面校验，必须给出被排除备选，非阻断也
不改谱。位置审视既可如实追索从既有材料和关系长出的内容，也可承认没有这种血缘、却
对完整作品全局必要的选择；不得为保留细节伪造因果，留白、静音或删除同样有效。最新策略以
`charter_settlement_profile=affirmative-promise-ledger-v1` 标识：决策显式携带宪章清偿，
对每一项宪章承诺以 kept / transformed / refused 交代，accept 必须全覆盖；清偿事件
指涉在每次读取时复验。整曲 fork 可把多个完整候选记为平行备选世界；它每次读取重算
ID，并复验 score Hash、event/part/range 与已记录候选，当前候选必须属于 branches。
它是稀疏的 whole-work alternative declaration，不是 epoch/LCA 谱系。新 accept 另冻结
当时对已记录 hard failure 的复核与相关 Hash；这不是当前 readiness 或审美证明。
基础 legacy、显式 Claim Lifecycle、acceptance-gated 与 settlement 历史均保持可读；
composition governance 与 revision contract profile 可独立存在或组合，旧非终态只在下一次
合法 transition 中单调升级且不可降级。修订合同在改动前冻结范围与撤回条件，下一轮显式
决定 promote challenger、保留基线或未决；机器只证明范围和闭环，不证明作品更好听。
`budget_exhausted` 只在正数冻结预算、fork 上限或历史上限确实达到时允许，其他终止理由
仍是终审 authority 声明而非机器证明。直接 `render` 与作者工程直接渲染继续可用，但
产物不会冒充 workflow 完成态。新增论证和分支保持稀疏，作品已经成立时应及时收束。
作品宪章与当前作品材料始终是核心；外部音乐宪法只是其后的无状态可选思想资源。完全
不使用它不会缺少展开图、复核、推导、证据、验收或续作功能，条款也不绑定这些环节。
任何旧 workflow binding 都仅保留不可变历史来源，不参与当前裁决，也不阻断继续创作；
其中 v0.1 已废弃，不再回查或映射到 v0.2。

文件型导入受显式输入根限制，Agent 不会因为连接服务就获得整机文件访问权限，也不能
把自己的决定标成创作者批准。

完整工具和客户端配置见 [MCP 接口](MCP.md)，状态机与诚信边界见
[可选创作工作流](创作工作流.md)。

## 已知限制

### 听感不能自动完成

技术报告可以帮助发现损坏、True Peak 余量、响度、相位、音域、频带、平衡、尾音
或候选差异，但不能判断旋律、结构、配器和作品是否成立。可选工作流证明复查过程，
不证明作品好听；最终版本仍需人耳 A/B。
完整边界见 [渲染后自检](渲染后自检.md)。

### 音质受资源限制

公开音源的采样质量、力度层、奏法与覆盖范围并不一致。程序合成更容易保持确定性
和连续性，也不等于复现真实乐器的全部细节。

### 首次渲染可能较慢

长曲、高采样率和多声部项目仍可能需要数分钟与较高峰值内存。`1.0.0` 的流式
分轨和自动并行会在证据充分时减少协调进程的分轨驻留并缩短部分冷渲染，但不会
突破既有内存、临时磁盘或全长混音预算。缓存主要加速后续重混；音符、奏法、资源
或有效乐器参数变化时，相关分轨仍需重新执行。

### 本机资源状态不同

“存在安装器”不等于资源已经下载且完整。源码包不携带大型采样，使用前请运行
环境诊断；部分安装、摘要不符或许可证据缺失都应修复，不能当作正常缺失跳过。

## 许可与输出

项目自研代码、DSP、CLI/MCP、Schema、测试和配置采用 Apache-2.0。第三方采样、
输入作品和最终音频保持各自的权利状态；天籁不会因为执行渲染而取得使用者音乐
输出的著作权。

发布音乐前，请检查 `许可与署名.json/.txt`、输入作品权利与上游资源条款。详情
见 [输出权利说明](../OUTPUT_RIGHTS.md)、
[项目名称与标识](../TRADEMARKS.md) 和
[音源许可政策](音源许可政策.md)。
